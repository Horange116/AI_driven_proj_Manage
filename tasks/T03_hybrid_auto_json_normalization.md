# T03 Task: Normalize hybrid-auto JSON outputs for DocReview

## 1. Background

This repository is for the PT9L DocReview project.

The project is not a generic document summarization task. The goal is to build an intelligent document review workflow for medical device project files, especially to check traceability and consistency between DHF and DMR documents.

Main review chain:

```text
DHF requirements / design inputs
  -> design plans / risk controls / verification / validation
  -> design outputs / drawings / BOM / inspection requirements
  -> DMR production process / work instructions / inspection / release requirements
```

Expected future findings include:

- duplicate or copied files
- missing downstream requirements
- parameter conflicts
- version inconsistencies
- broken traceability
- design requirements not reflected in production or inspection files

The current task is T03: build a unified structured JSON layer that downstream code can use for search, indexing, comparison, and evidence-based review.

## 2. New current situation

Earlier planning assumed the T03 input would mainly be Markdown generated by MinerU / skill processing.

However, the repository now contains hybrid-auto processing results. These outputs already include many JSON files, especially files like:

```text
data_Processed/DHF -梳理版_预处理_hybrid-auto处理/.../office/..._content_list.json
```

Example inspected file:

```text
data_Processed/DHF -梳理版_预处理_hybrid-auto处理/01 立项批准书E0/客户需求书(封面)E0/office/客户需求书(封面)E0_content_list.json
```

The inspected JSON has this rough structure:

```json
[
  {
    "type": "table",
    "table_caption": [],
    "table_body": "<table>...</table>",
    "page_idx": 0
  },
  {
    "type": "header",
    "text": "文件编号: <u>PT9L-KHXQ01</u> V1.0 客户需求书 表号: QR-7.3-01/E0",
    "page_idx": 0
  }
]
```

This confirms that hybrid-auto JSON is usable as raw parser output, but it is not yet the final DocReview normalized JSON.

## 3. Key distinction

Current hybrid-auto JSON means:

```text
parser-level output
```

It tells us what the parser saw on the page: blocks, tables, headers, HTML table bodies, and page indexes.

T03 normalized JSON should mean:

```text
review-system data foundation
```

It should make each document easy to identify, search, compare, and cite as evidence.

Main difference:

| Dimension | Current hybrid-auto JSON | T03 normalized JSON |
|---|---|---|
| Source | Generated by parser | Defined by this project |
| Main focus | Page/layout/text blocks | Review, traceability, evidence |
| Document identity | Mostly implied by path | Explicit fields |
| Table content | Often HTML string | Preserve raw HTML and extract plain text |
| Downstream usability | Raw material | Direct input for indexing/checking |
| Final format | No | Yes, for T03 |

## 4. T03 goal

Convert hybrid-auto raw JSON files into a project-defined normalized JSON format.

Do not restart full raw document parsing.

Do not immediately perform DHF/DMR consistency review.

First build a stable normalized data layer.

Recommended pipeline:

```text
hybrid-auto raw JSON
  -> inspect representative samples
  -> define normalized schema
  -> implement converter
  -> generate normalized JSON outputs
  -> later use for retrieval, comparison, and review findings
```

## 7. Minimum normalized schema proposal

Use this as the first target schema. Keep it small and robust.

```json
{
  "doc_id": "DHF_01_客户需求书_封面_E0",
  "dataset": "DHF",
  "stage": "01 立项批准书E0",
  "document_name": "客户需求书(封面)E0",
  "parse_backend": "hybrid-auto",
  "source_json_path": "data_Processed/.../xxx_content_list.json",
  "source_original_path": null,
  "blocks": [
    {
      "block_id": "b0001",
      "block_order": 1,
      "type": "table",
      "page_idx": 0,
      "text": "plain text extracted from table html",
      "raw_html": "<table>...</table>",
      "source_anchor": {
        "json_path": "data_Processed/.../xxx_content_list.json",
        "page_idx": 0,
        "block_order": 1
      }
    }
  ],
  "extracted_fields": {
    "document_code": null,
    "version": null,
    "product_model": null,
    "project_no": null,
    "product_name": null,
    "form_no": null
  }
}
```

Notes:

- `doc_id` should be deterministic and stable.
- `dataset` should be inferred from path: DHF or DMR.
- `stage` should usually be inferred from the first folder level under the hybrid-auto processed folder.
- `document_name` should usually be inferred from the document folder name or JSON filename.
- `parse_backend` should be `hybrid-auto`.
- Preserve raw parser content when useful, especially table HTML.
- Always create plain `text` for search and later LLM review.

## 8. Required conversion behavior

For each `*_content_list.json`:

1. Load the JSON safely.
2. Determine document metadata from the path.
3. Iterate blocks in original order.
4. Convert each block into a normalized block.
5. Preserve original block type.
6. Extract plain text:
   - for `text`, use text directly
   - for `table_body`, strip HTML tags while preserving readable cell text
   - for unknown fields, fall back to a safe string representation only if useful
7. Preserve raw HTML in `raw_html` for table blocks.
8. Preserve `page_idx` if present.
9. Create `source_anchor` for every block.
10. Write one normalized JSON per source document.

## 9. Suggested output location

Do not overwrite hybrid-auto raw results.

Write normalized outputs to a separate folder, for example:

```text
outputs/normalized_json/
```

Suggested structure:

```text
outputs/normalized_json/
  DHF/
    ...
  DMR/
    ...
```

Also consider writing a small manifest:

```text
outputs/normalized_json/manifest.json
```

The manifest can contain:

```json
{
  "total_source_json": 0,
  "converted": 0,
  "failed": 0,
  "failures": []
}
```

## 10. What not to do

Do not modify original files under `data_Processed/`.

Do not delete, move, or overwrite hybrid-auto results.

Do not rerun full parsing unless explicitly requested.

Do not use Hermes/Kimi or another LLM to scan the whole repository.

Do not attempt full DHF/DMR review findings in this task.

Do not make the schema too complex before sample inspection.

## 12. Acceptance criteria

The task is acceptable when:

- At least one DHF hybrid-auto JSON is converted successfully.
- At least one DMR hybrid-auto JSON is converted successfully, if DMR hybrid-auto input exists.
- Table HTML is preserved in `raw_html`.
- Plain searchable text is extracted into `text`.
- Every block has `block_id`, `block_order`, `type`, `page_idx`, and `source_anchor`.
- The original hybrid-auto files are not modified.
- The output is written under `outputs/`, not under `data_Processed/`.

## 13. Why this task matters

The later review system needs stable evidence objects.

Without T03 normalization, downstream checks would need to understand every parser-specific format directly.

With T03 normalization, later tasks can focus on domain review logic, such as:

```text
DHF requirement says accuracy must be +/-0.2 C.
DMR inspection file says +/-0.5 C or omits this requirement.
Then generate a finding candidate with both evidence anchors.
```
