# T03 Task: Normalize hybrid-auto JSON outputs for DocReview

## 1. Background

This repository is for the PT9L DocReview project.

The project is not a generic document summarization task. The goal is to build an intelligent document review workflow for medical device project files, especially to check traceability and consistency between DHF and DMR documents.

Main review chain:

```text
DHF requirements / design inputs
  -> design plans / risk controls / verification / validation
  -> design outputs / drawings / BOM / inspection requirements
  -> DMR production process / work instructions / inspection / release requirements
```

Expected future findings include:

- duplicate or copied files
- missing downstream requirements
- parameter conflicts
- version inconsistencies
- broken traceability
- design requirements not reflected in production or inspection files

The current task is T03: build a unified structured JSON layer that downstream code can use for search, indexing, comparison, and evidence-based review.

## 2. Current situation

However, the repository now contains hybrid-auto processing results under `data_Processed/`. The important folders are expected to be:


A path inventory has also been added:

```text

```

The path inventory shows that hybrid-auto output is usually organized as grouped JSON files per source document. A typical processed document directory contains:

```text

*_content_list_v2.json

```

Office-origin documents are usually under:

```text

```

PDF/image-origin documents are usually under:

```text

```

Therefore, T03 should no longer assume that `*_content_list.json` is the only or primary input.

## 3. Input priority decision

For each processed document, use this priority:

```text
1. Prefer *_content_list_v2.json as the main parser output.
2. If *_content_list_v2.json is missing, fall back to *_content_list.json.
3. Keep *_middle.json and *_model.json paths as auxiliary metadata/diagnostic references.
4. Do not convert both v1 and v2 into duplicate normalized documents for the same source document.
```

Rationale:

- `*_content_list_v2.json` is more structured and preserves nested content such as `content.html`, `page_header`, and `page_footer`.
- `*_content_list.json` is still useful as a fallback because it has a simpler block list shape.
- `*_middle.json` and `*_model.json` may contain layout/model intermediate data, but they should not be the first T03 normalized-text source unless later inspection proves they are needed.

## 4. Known raw JSON shapes

### 4.1 content_list.json shape

Observed rough structure:

```json
[
  {
    "type": "table",
    "table_caption": [],
    "table_body": "<table>...</table>",
    "page_idx": 0
  },
  {
    "type": "header",
    "text": "文件编号: ...",
    "page_idx": 0
  }
]
```

Important fields:

```text
type
table_body
text
page_idx
table_caption
```

Typical extraction rules:

```text
table_body -> raw_html and plain text
text -> plain text
header/footer type -> header/footer block
page_idx -> page index
```

### 4.2 content_list_v2.json shape

Observed rough structure:

```json
[
  [
    {
      "type": "table",
      "content": {
        "table_caption": [],
        "html": "<table>...</table>",
        "table_type": "simple_table",
        "table_nest_level": 1
      }
    },
    {
      "type": "page_header",
      "content": {
        "page_header_content": [
          {"type": "text", "content": "文件编号:"},
          {"type": "text", "content": " PT9L-KFJH01", "style": ["underline"]}
        ]
      }
    }
  ]
]
```

Important fields:

```text
type
content
content.html
content.page_header_content
content.page_footer_content
content.table_caption
content.table_type
content.table_nest_level
```

Typical extraction rules:

```text
content.html -> raw_html and plain text
content.page_header_content -> header text
content.page_footer_content -> footer text
nested page list -> flatten into ordered blocks
outer list index -> page_idx if explicit page_idx is missing
```

## 5. Key distinction

Current hybrid-auto JSON means:

```text
parser-level output
```

It tells us what the parser saw on the page: blocks, tables, headers, HTML table bodies, and page/page-like structure.

T03 normalized JSON should mean:

```text
review-system data foundation
```

It should make each document easy to identify, search, compare, and cite as evidence.

Main difference:

| Dimension | Current hybrid-auto JSON | T03 normalized JSON |
|---|---|---|
| Source | Generated by parser | Defined by this project |
| Main focus | Page/layout/text blocks | Review, traceability, evidence |
| Document identity | Mostly implied by path | Explicit fields |
| Table content | HTML or nested content object | Preserve raw HTML and extract plain text |
| Header/footer | Parser-specific type names | Normalized block types |
| Downstream usability | Raw material | Direct input for indexing/checking |
| Final format | No | Yes, for T03 |

## 6. T03 goal

Convert hybrid-auto raw JSON files into a project-defined normalized JSON format.

Do not restart full raw document parsing.

Do not immediately perform DHF/DMR consistency review.

First build a stable normalized data layer.

Recommended pipeline:

```text
hybrid-auto JSON group
  -> group files by source document directory
  -> choose main input: content_list_v2 first, fallback to content_list
  -> normalize blocks
  -> preserve source anchors and auxiliary JSON paths
  -> generate normalized JSON outputs
  -> later use for retrieval, comparison, and review findings
```

## 9. Minimum normalized schema proposal

Use this as the first target schema. Keep it small and robust.

```json
{
  "doc_id": "DHF_01_客户需求书_封面_E0",
  "dataset": "DHF",
  "stage": "01 立项批准书E0",
  "document_name": "客户需求书(封面)E0",
  "parse_backend": "hybrid-auto",
  "source_json_path": "data_Processed/.../xxx_content_list_v2.json",
  "fallback_source_json_path": null,
  "auxiliary_json_paths": {
    "content_list": "data_Processed/.../xxx_content_list.json",
    "middle": "data_Processed/.../xxx_middle.json",
    "model": "data_Processed/.../xxx_model.json"
  },
  "source_original_path": null,
  "blocks": [
    {
      "block_id": "b0001",
      "block_order": 1,
      "type": "table",
      "raw_type": "table",
      "page_idx": 0,
      "text": "plain text extracted from table html",
      "raw_html": "<table>...</table>",
      "source_anchor": {
        "json_path": "data_Processed/.../xxx_content_list_v2.json",
        "page_idx": 0,
        "block_order": 1
      }
    }
  ],
  "extracted_fields": {
    "document_code": null,
    "version": null,
    "product_model": null,
    "project_no": null,
    "product_name": null,
    "form_no": null
  }
}
```

Notes:

- `doc_id` should be deterministic and stable.
- `dataset` should be inferred from path: DHF or DMR.
- `stage` should usually be inferred from the first folder level under the hybrid-auto processed folder.
- `document_name` should usually be inferred from the document folder name or JSON filename.
- `parse_backend` should be `hybrid-auto`.
- `source_json_path` should point to the chosen main input, preferably `*_content_list_v2.json`.
- `auxiliary_json_paths` should preserve related `content_list`, `middle`, and `model` paths when present.
- Preserve raw parser content when useful, especially table HTML.
- Always create plain `text` for search and later LLM review.

## 10. Required conversion behavior

For each processed document directory:

1. Discover the JSON group for the same source document.
2. Prefer `*_content_list_v2.json` as main input.
3. If v2 is absent, use `*_content_list.json` as fallback.
4. Do not generate duplicate normalized documents from both v1 and v2.
5. Record `*_middle.json` and `*_model.json` paths as auxiliary references.
6. Load the selected main JSON safely.
7. Determine document metadata from the path.
8. Flatten parser blocks into a single ordered `blocks` list.
9. Preserve original parser type in `raw_type`.
10. Normalize block type into stable project types such as:
    - heading
    - paragraph
    - table
    - image
    - header
    - footer
    - list
    - unknown
11. Extract plain text:
    - for v1 `text`, use text directly
    - for v1 `table_body`, strip HTML tags while preserving readable cell text
    - for v2 `content.html`, strip HTML tags while preserving readable cell text
    - for v2 `page_header_content`, join nested text fragments into header text
    - for v2 `page_footer_content`, join nested text fragments into footer text
    - for other nested content, extract useful text conservatively
12. Preserve raw HTML in `raw_html` for table blocks.
13. Preserve `page_idx` if present.
14. If `page_idx` is absent in v2, infer it from the outer page-list index when possible.
15. Create `source_anchor` for every block.
16. Write one normalized JSON per source document.

## 14. Acceptance criteria

The task is acceptable when:

- At least one DHF `*_content_list_v2.json` is converted successfully.
- At least one DMR `*_content_list_v2.json` is converted successfully, if DMR v2 input exists.
- At least one `*_content_list.json` fallback path is tested or explicitly confirmed unnecessary.
- Table HTML from either `table_body` or `content.html` is preserved in `raw_html`.
- Plain searchable text is extracted into `text`.
- Page headers and footers are converted into normalized header/footer blocks when present.
- Every block has `block_id`, `block_order`, `type`, `raw_type`, `page_idx`, and `source_anchor`.
- Related `_middle.json` and `_model.json` paths are recorded when present.
- The original hybrid-auto files are not modified.
- The output is written under `outputs/`, not under `data_Processed/`.
- The same source document is not duplicated due to both v1 and v2 being present.

## 15. Why this task matters

The later review system needs stable evidence objects.

Without T03 normalization, downstream checks would need to understand every parser-specific format directly.

With T03 normalization, later tasks can focus on domain review logic, such as:

```text
DHF requirement says accuracy must be +/-0.2 C.
DMR inspection file says +/-0.5 C or omits this requirement.
Then generate a finding candidate with both evidence anchors.
```
