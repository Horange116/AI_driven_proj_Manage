## 3. S1 文件解析标准化

### 3.1 目标

把已有 Markdown / page-level Markdown / MinerU 结果统一转成稳定 JSON。此阶段不做复杂语义判断，只保证机器可读、可追溯、可评估。

### 3.2 输入

- `data_Processed/**/auto/*.md`
- 已有文件 manifest
- 已有 duplicates report

### 3.3 输出

```text
outputs/normalized/{doc_id}.json
outputs/normalized/quality_report.json
schemas/normalized_document.schema.json
harness/reports/parse_report.json
```

### 3.4 normalized JSON 最小字段

```json
{
  "doc_id": "string",
  "source_path": "string",
  "file_name": "string",
  "doc_type_hint": "string",
  "hash": "string",
  "parser": "mineru|vlm|markdown|unknown",
  "blocks": [
    {
      "block_id": "string",
      "type": "title|paragraph|table|list|page_marker|unknown",
      "text": "string",
      "page": null,
      "section_path": [],
      "anchor": {
        "doc_id": "string",
        "source_path": "string",
        "block_id": "string",
        "char_start": 0,
        "char_end": 0
      }
    }
  ],
  "tables": [],
  "quality": {
    "text_length": 0,
    "block_count": 0,
    "empty_ratio": 0,
    "ocr_suspect": false
  }
}
```

### 3.5 parse_harness 要求

Codex 实现：

```bash
python -m src.docreview.harness.runner --stage parse --cases harness/cases/parse_public.jsonl
```

评估项：

- JSON schema 是否通过
- doc_id 是否稳定
- block 数是否非零
- evidence anchor 是否存在
- 空文件 / 解析失败是否被记录，而不是静默跳过

完成标准：

```text
parse_harness pass_rate >= 0.95
所有失败样例写入 harness/reports/parse_failures.jsonl
```

## 4. S2 文件语义抽取

### 4.1 目标

从 normalized JSON 中提取可用于复核的语义单元，而不是只停留在全文文本。

### 4.2 优先抽取对象

| 类型 | 示例 | 用途 |
|---|---|---|
| document_role | 设计输入、风险分析、验证报告、检验规范 | 判断上下游关系 |
| version | V1.0、Rev.A、发布日期 | 多版本检测 |
| parameter | 电压 5V、精度 ±0.2°C、温度范围 | 参数漂移检测 |
| requirement | 应当、必须、需满足 | 追溯链源头 |
| verification | 测试项、判定标准、结果 | 需求验证关系 |
| risk_control | 风险、措施、残余风险 | 风险闭环 |
| component | 主板、探头、包装、标签 | 跨文件实体对齐 |
| table_field | 表格字段名与字段值 | 结构化对齐 |

### 4.3 输出

```text
outputs/semantics/semantic_units.jsonl
outputs/semantics/entities.jsonl
outputs/semantics/relations.jsonl
schemas/semantic_unit.schema.json
harness/reports/semantic_report.json
```

### 4.4 semantic_harness 要求

评估命令：

```bash
python -m src.docreview.harness.runner --stage semantic --cases harness/cases/semantic_public.jsonl
```

评估项：

- 是否能从指定文档抽出目标参数
- 是否能保留原文 evidence anchor
- 参数单位是否规范化
- 版本号是否规范化
- document_role 是否基本正确

完成标准：

```text
semantic_harness micro_f1 >= 0.75
关键字段 evidence_anchor 覆盖率 >= 0.95
```

实现策略：

1. 先用规则和正则抽取版本、日期、参数、单位。
2. 再用轻量 LLM 处理 document_role、复杂表格语义、同义参数归一。
3. 所有 LLM 结果必须记录 prompt、model、tokens、cost、confidence。

## 5. S3 单文件内部语义一致性

### 5.1 目标

判断一份文件内部是否自洽。

### 5.2 检测类型

| finding type | 说明 | 推荐层级 |
|---|---|---|
| placeholder_unfilled | XX、待填写、N/A、模板字段未填 | L0 |
| internal_param_conflict | 同一文件内部同一参数出现多个值 | L1 |
| version_date_conflict | 版本号、发布日期、修订记录不一致 | L1 |
| table_text_conflict | 表格和正文描述冲突 | L1/L2 |
| abnormal_value | 数量级明显异常 | L1/L2 |
| template_pollution_single | 文件残留其他项目/其他产品信息 | L1/L2 |

### 5.3 输出

```text
outputs/findings/intra_doc_findings.jsonl
harness/reports/intra_doc_report.json
```

### 5.4 finding 最小字段

```json
{
  "finding_id": "F-INTRA-000001",
  "scope": "intra_doc",
  "type": "internal_param_conflict",
  "severity": "high|medium|low",
  "confidence": 0.0,
  "tier": "L0|L1|L2|L3",
  "source": "rule_id_or_agent_name",
  "summary": "string",
  "evidence": [],
  "recommendation": "string",
  "review_status": "pending"
}
```

### 5.5 intra_doc_harness 要求

```bash
python -m src.docreview.harness.runner --stage intra_doc --cases harness/cases/intra_doc_public.jsonl
```

评估项：

- finding type 是否正确
- evidence 是否命中预期文档和片段
- severity 是否合理
- false positive 是否可控

完成标准：

```text
precision >= 0.80
recall >= 0.60
所有误报写入 docs/bad_cases/intra_doc_bad_cases.md
```

## 6. S4 文件和文件之间的信息语义一致性

### 6.1 目标

判断不同文件之间是否存在语义冲突或信息断裂。

### 6.2 检测类型

| finding type | 说明 | 推荐层级 |
|---|---|---|
| cross_doc_param_conflict | 同一参数跨文件取值冲突 | L1/L2 |
| requirement_verification_mismatch | 需求和验证标准不一致 | L2/L3 |
| design_output_mismatch | 设计输出与输入/验证不一致 | L2/L3 |
| dmr_dhf_conflict | 研发要求与生产/检验文件冲突 | L2/L3 |
| missing_downstream_trace | 上游需求没有下游验证或生产体现 | L2/L3 |

### 6.3 输出

```text
outputs/findings/inter_doc_findings.jsonl
harness/reports/inter_doc_report.json
```

### 6.4 inter_doc_harness 要求

```bash
python -m src.docreview.harness.runner --stage inter_doc --cases harness/cases/inter_doc_public.jsonl
```

评估项：

- 是否找到冲突双方或多方
- 是否能说明冲突字段
- 是否给出双方 evidence
- 是否避免把同义表达误判为冲突

完成标准：

```text
precision >= 0.75
recall >= 0.55
evidence_pair_coverage >= 0.90
```

实现策略：

1. 用知识层先召回候选，不允许直接把全库塞给 LLM。
2. 参数冲突优先规则判断。
3. 同义归一、上下游语义判断再升级 LLM。
4. 所有跨文档 finding 必须至少有两个 evidence anchors。

## 8. S6 端到端 + 分级路由

### 8.1 目标

把 S1-S5 串成一条命令可以跑的 pipeline，并实现 L0/L1/L2/L3 成本分级。

### 8.2 端到端命令

Codex 实现：

```bash
python -m src.docreview.pipeline.run_review \
  --config configs/default.yaml \
  --input data_Processed \
  --output outputs \
  --stages parse,semantic,intra_doc,inter_doc,pattern,merge
```

支持：

```bash
# 只跑某阶段
python -m src.docreview.pipeline.run_review --stage semantic

# 跑 harness
python -m src.docreview.harness.runner --stage all

# 生成成本报表
python -m src.docreview.routing.cost_tracker --report outputs/reports/cost.json
```

### 8.3 分级路由规则

| 层级 | 使用对象 | 进入条件 | 输出要求 |
|---|---|---|---|
| L0 | 纯规则 | hash、空文本、占位符、正则可判定问题 | 无 LLM 成本 |
| L1 | 结构化规则 + 知识层 | 参数、版本、字段级对齐 | 查询证据完整 |
| L2 | LLM 单点判断 | 单文件复杂语义、同义归一、表格正文冲突 | 记录 prompt/cost/confidence |
| L3 | 多 Agent 综合判断 | 追溯断链、DHF-DMR复杂冲突、多证据综合 | 记录推理摘要与升级原因 |

升级机制：

```text
if confidence < threshold:
    upgrade_to_next_tier
if evidence_missing:
    do_not_emit_finding; emit_candidate_for_review
if estimated_cost > budget:
    skip_LLM_and_emit_low_confidence_candidate
```

### 8.4 输出

```text
outputs/findings/findings.jsonl
outputs/reports/run_report.json
outputs/reports/cost.json
outputs/reports/harness_summary.json
outputs/reports/ai_usage_log.jsonl
```

### 8.5 e2e_harness 要求

```bash
python -m src.docreview.harness.runner --stage e2e --cases harness/cases/e2e_public.jsonl
```

完成标准：

```text
pipeline_exit_code = 0
schema_pass_rate = 1.0
finding_schema_pass_rate = 1.0
cost_report_exists = true
harness_summary_exists = true
每个 finding 都有 tier/source/evidence/confidence
```

## 11. 给 Codex 的约束

执行时必须遵守：

1. 不要删除已有数据文件。
2. 不要重跑耗时解析，优先消费已有 Markdown。
3. 不要把 LLM 接入 S1 主流程。
4. 每个阶段必须先有 schema，再有输出，再有 harness。
5. 每个 detector 必须能单独运行，也必须能进入 pipeline。
6. 所有 finding 必须带 evidence anchor。
7. 所有 LLM 调用必须走 routing/cost_tracker，不允许散落在业务代码中。
8. 每次新增阶段，都要同步更新 `DocReview_任务状态卡.md`。
